# 文章发布流水线 (Article Review Pipeline)

利用 git 作为流转记录，通过独立 Agent 实现客观审稿。

## 核心模型：母稿 + 平台分叉

- **原稿 = 母稿（真相源）**：一次写就，通过审稿后作为所有平台版本的派生起点。
- **关键纠正（本技能存在的意义）**：博客版与公众号版必须是**内容不同**的两个版本，而不是"同一份 MD 渲博客、同一份转 html"——后者只是格式不同，内容雷同，失去了分平台的价值。
  - **技术深度版**（发博客 / 知乎）：保留并适度扩展代码、技术细节、严谨论证，不强制口语化，适合"收藏当笔记"。
  - **公众号友好版**（发公众号）：卡兹克风格优化（钩子开头、口语化、情绪共鸣、适配手机阅读）。
- 两个版本从**同一份原稿分别派生**，落点不同、互不覆盖。

## 触发词

发布流程、文章流水线、审稿、过审、走流水线、开始写文章、帮我写公众号

## 环境变量（运行前由用户环境注入）

本技能刻意不硬编码任何个人仓库名、个人发布记录表。以下变量由宿主环境 / 用户在使用前提供：

- `BLOG_REPO`：技术深度版与公众号产物的博客仓库（如 `your-blog-repo`）。默认约定下两版都落在此仓库内。
- `PUBLISH_TRACKER`：发布记录表标识（如飞书多维表格的表名 / ID）。阶段 4 按平台写入发布记录。

> 若环境未提供，技能在首次用到时**主动询问用户**这两个值，不臆测。

## 全局规则

- **每次审稿必须使用独立 Agent 执行**（非当前对话的主 AI），避免自己审自己
- **每次审稿必须传入 `review-rubric.md` 作为参考标准**
- **用户说"通过"时，必须提醒："文章已通过审稿，请提交 git 后继续。"**
- 不新建状态目录、不创建 JSON 状态文件——git commit 就是状态（内容输出目录如 `source/wechat/` 按本技能约定创建）
- round 计数靠口头记录，原稿最多 3 轮，各平台版本优化最多 2 轮

## 流程

### 阶段 1：原稿（母稿）

1. 用户给素材 / 选题 / 想法
2. AI 根据选题判断 HKR 质量：H（有趣 / 悬念）、K（知识密度）、R（共鸣感），至少过 2/3 才能进入写作
3. 写出原稿，保存到 `source/drafts/`
4. 提示用户："原稿已写好，请 review 并提交 git。"
5. 用户提交后，AI 审稿（见审稿标准 L1+L1a+L2+L3+L4）
6. 输出修改建议，用户修改后提交
7. 独立 Agent 再次审稿，重复至多 3 轮
8. 用户说"通过"时提醒提交，然后进入阶段 2

### 阶段 2：平台分发决策（关键，解决博客 / 公众号内容雷同）

1. 询问用户：**本文发哪些平台？**（可多选）
   - [ ] 公众号（需要公众号友好版 + 封面）
   - [ ] 知乎（需要技术深度版）
   - [ ] 博客（Hexo `source/_posts/`，需要技术深度版）
   - （可选）[ ] 其他站点（技术深度版，落点由用户指定）
2. 根据选择，从**同一份原稿分别派生**对应版本（见下方"版本派生规则"），互不覆盖。
3. 每个被选平台进入各自的优化 / 发布子流程（阶段 3）。

> **默认约定（方案 A：单仓库双输出）**
> - 技术深度版（博客 / 知乎）→ Hexo `source/_posts/{date}-{title}.md`
> - 公众号友好版 → 先存 `source/wechat/{title}.md`（khazix 优化版，可 review / 手改），再经 `wechat-post-html` 转为 `source/html/{title}.html`
> 两者都在 `${BLOG_REPO}` 仓库内，不引入第二个站点、不增加部署负担。

#### 版本派生规则

**A. 技术深度版（博客 / 知乎 / 其他工程站）**
- 目标：信息密度高、可复现、适合"收藏当笔记"。
- 保留并适度扩展：代码示例、命令、配置片段、版本号、踩坑细节、参考链接。
- 结构：可带"背景 / 方案 / 实现 / 坑 / 结论"等技术实录结构；开头可平实，不必强求钩子。
- **不强制口语化，不追求情绪共鸣**（这是与公众号版最根本的区别）。
- 落点：`source/_posts/{date}-{title}.md`，frontmatter 含 `title / date / author / tags / summary`。
- 优化方式：做一次**技术校对**（代码可运行性、术语准确、链接有效、版本号核对），**不**调用卡兹克风格优化。
- 知乎：用户直接从这份 `_posts` MD 复制粘贴发布（知乎原生支持 Markdown）。

**B. 公众号友好版**
- 目标：手机端可读、有钩子、有情绪、能转发。
- 调用 `khazix-writer` 技能做风格优化：钩子开头、口语化、节奏、共鸣、立场。
- 长代码 / 大段配置可精简或截图化，优先叙事与观点，降低阅读门槛。
- 落点（两档，不丢中间版本）：
  1. 先存 **khazix 优化版 .md** 到 `source/wechat/{title}.md` —— 公众号专属稿件，用户可 review / 手改，单独提交 git。
  2. 再经 `wechat-post-html` 将上面这份 .md 转换为 `source/html/{title}.html`。
- 优化方式：卡兹克风格优化（审稿标准 L1-L4 严格版 + L5 优化效果验证），最多 2 轮。

### 阶段 3：各平台优化 & 发布

**3a. 博客 / 知乎（技术深度版）**
1. 对 `source/_posts/` 中的技术深度版做"技术校对"（**非**卡兹克风格优化）
2. 用户 review，修改后提交
3. （可选）独立 Agent 审稿，最多 2 轮
4. 用户说"通过"时提醒提交
5. 发布：博客由 Hexo 构建发布；知乎由用户从 `_posts` MD 直接复制发布
6. 确认后复制到 `source/published/`（如有该目录）作为存档

**3b. 公众号（公众号友好版）**
1. 调用 `khazix-writer` 对原稿（或技术版的精简稿）做风格优化，写出 `source/wechat/{title}.md`
2. 用户 review diff（针对这份公众号稿 .md），修改后提交
3. AI 审稿（L1-L4 严格版 + L5），最多 2 轮
4. 用户说"通过"时提醒提交
5. 调用 `wechat-cover-skill` 生成封面（3 张可选），用户挑选最佳版本
6. 调用 `wechat-post-html` 将 `source/wechat/{title}.md` 转换为 `source/html/{title}.html`
7. 更新飞书待办状态（调用 `${PUBLISH_TRACKER}` 协议，平台填"公众号"）
8. 发布到公众号

### 阶段 4：发布记录

- 每发一个平台，更新 `${PUBLISH_TRACKER}` 飞书多维表格"发布记录"；平台字段与阶段 2 的选择一一对应（公众号 / 知乎 / 博客 / 其他）。
- 技术深度版与公众号友好版是**两条独立记录**（即便来自同一篇原稿），便于复盘各平台表现。

## 审稿执行协议

每轮审稿的执行步骤：

1. 读取待审文件
2. 使用独立 Agent 执行审稿，prompt 中：
   - 说明审稿角色（你不是作者，是独立审稿人）
   - 附带 `review-rubric.md` 全文作为参考
   - 要求输出结构化审稿报告
3. 将审稿报告交给用户
4. 用户决定修改或说"通过"

## 输出格式

每次审稿报告必须包含：

```markdown
### 审稿报告 — 第 N 轮

#### L1 硬性规则
- [ ] L1-1 违禁词：通过/不通过（问题列表）
- [ ] L1-2 违禁标点：通过/不通过（问题列表）
- [ ] L1-3 结构八股：通过/不通过（问题列表）
- [ ] L1-4 模糊工具名：通过/不通过（问题列表）

#### L2 风格一致性
- [ ] 开场：通过/不通过
- [ ] 节奏：通过/不通过
- [ ] 口语化：通过/不通过
- [ ] 标点复核：通过/不通过

#### L3 内容质量
- [ ] 观点支撑：通过/不通过
- [ ] 知识输出：通过/不通过
- [ ] 文化升华：通过/不通过
- [ ] 对立观点共情：通过/不通过

#### L4 活人感
- [ ] 温度：通过/不通过
- [ ] 独特性：通过/不通过
- [ ] 立场：通过/不通过
- [ ] 流畅度：通过/不通过

#### 本轮总结
- 通过项：X/Y
- 未通过项及修改建议（按优先级排序）
```
